# Astro — Design Proposal

A personal astrology application: accurate offline chart calculation, interactive
chart graphics, synastry and transits, saved charts, and multi-style psychological
interpretation. This document reviews the platform options, sets out a feasible
implementation route, and covers every point of the specification.

*Status: proposal v1 · 2026-07-04 · decisions taken with Matthew: web-first PWA,
hybrid interpretation engine with aspect-combination logic, extended body set,
private GitHub repo `fairflow/astro`.*

---

## 0. Recommendation in one paragraph

Build a **local-first Progressive Web App (PWA)**: a static bundle of
HTML/TypeScript/SVG that computes everything client-side, stores charts in the
browser's IndexedDB, and works fully offline once installed. It is served from any
simple host (a subdirectory of an existing WordPress/Krystal site is enough — no
dedicated server, no server-side code required), develops and tests natively on
the MacBook with a dev server, and installs to iPad and Android home screens
directly from Safari/Chrome. If a genuinely native feel is wanted later, the same
codebase wraps into iPadOS/Android apps via Capacitor. Ephemeris accuracy comes
from a two-tier provider: the MIT-licensed `astronomy-engine` for Sun–Pluto
(±1 arcminute), plus **compact Chebyshev coefficient packs generated from JPL
Horizons data** (public domain) for Chiron, Ceres, Pallas, Juno, Vesta and Eris —
all bundled, so no internet is needed to cast a chart. Swiss Ephemeris (AGPL or
CHF 750 commercial licence) remains available as an optional high-precision
plug-in, validated against in tests but not required at runtime.

## 1. Platform options review & feasibility

### The three candidate targets

| | Web app (simple host) | Native iPadOS | Native Android |
|---|---|---|---|
| Language/stack | TypeScript + SVG, static files | Swift/SwiftUI | Kotlin/Compose |
| Server requirements | **None beyond static file hosting** — works in a subdirectory of a WordPress site; optional small Python/PHP endpoints possible but not needed | n/a (App Store or ad-hoc install) | n/a (Play Store or side-load) |
| Offline capability | Full, via service worker + bundled ephemeris packs + IndexedDB | Full | Full |
| Testable on the MacBook | **Directly** — any browser + `python3 -m http.server` or Vite dev server | Xcode simulator (good) | Android Studio emulator (heavier) |
| Effort to reach the other targets | Near zero: PWA installs on iPad & Android today; Capacitor wrapper later if store presence wanted | Rewrite for each other target | Rewrite for each other target |
| Distribution friction | Just a URL | Apple Developer account ($99/yr), review | Play account ($25), review |
| Risk | Browser storage eviction (mitigated: export/import + `navigator.storage.persist()`) | Two more codebases if web also wanted | Same |

**Decision (agreed): web-first PWA.** The targets are not mutually exclusive
precisely because a PWA covers all three at once: it runs in a browser on the
MacBook during development, is served from a simple host online, and installs
offline-capable on iPad and Android. The one thing a PWA cannot do is appear in
the App Store — if that matters later, Capacitor wraps the identical codebase
into store-submittable iPad and Android apps (weeks, not months, of extra work).

### Local development & testing on the MacBook

- `npm run dev` (Vite) → hot-reloading app at `http://localhost:5173`.
- Zero-dependency fallback: the mock-up in this repo runs from a plain
  `python3 -m http.server` — no Node required to view it.
- Unit tests (Vitest) run headless; ephemeris golden tests compare computed
  positions against reference values generated by a small **Python validation
  harness** (Skyfield + JPL DE440s + Horizons queries), kept in `tools/`.
- iPad testing during development: Safari on the iPad pointed at the MacBook's
  LAN address, or the Xcode iOS Simulator.

### Hosting scenarios

1. **Simple shared host (e.g. alongside WordPress on Krystal)** — copy the built
   `dist/` folder to a subdirectory. HTTPS (required for service workers) is
   already provided by the host. WordPress itself is not involved; the app just
   lives next to it. ✅ cheapest, recommended.
2. **Static-host CDN (GitHub Pages / Cloudflare Pages, private-ish via unlisted
   URL)** — same build, `git push` deploys. ✅ good for staging.
3. **Dedicated server** — explicitly out of scope per spec; nothing here needs it.

A note on licences and hosting: because the app is distributed to browsers,
anything AGPL-licensed in the bundle (i.e. Swiss Ephemeris) would oblige
source-code release of the whole app. The default build avoids this entirely
(see §2); the Swiss Ephemeris plug-in is opt-in and only for private use.

## 2. Ephemeris (spec 1)

### Accuracy requirement

For astrological work the practical bar is ~0.1° (6 arcminutes) — orbs are
measured in whole degrees, and even fast movers (the Moon at ~13°/day) shift only
~0.03° per 3 minutes of birth-time uncertainty, which dwarfs any model error
below an arcminute. All options below beat the bar for the planets; the work is
in the asteroids and Eris.

### Options considered

| Option | Bodies | Accuracy | Size | Licence | Offline | Verdict |
|---|---|---|---|---|---|---|
| **astronomy-engine** (npm) | Sun–Pluto, Moon | ±1′ vs NOVAS, years 1700–2200 | ~120 KB | MIT | yes | ✅ core provider |
| **Own Chebyshev packs from JPL Horizons** | any small body (Chiron, Ceres, Pallas, Juno, Vesta, Eris) | ~1″ vs Horizons over fitted span | ~30–80 KB per body per 2 centuries | data public domain, code ours | yes | ✅ asteroid provider |
| Swiss Ephemeris (WASM) + `.se1` files | everything incl. all asteroids | reference grade (based on JPL DE431) | ~2 MB WASM + data files | **AGPL or CHF 750**; ephemeris files may not be redistributed without Astrodienst's written permission | yes | ⚠️ optional plug-in, private use / validation only |
| Skyfield + DE440s (Python, server-side) | everything via SPK kernels | reference grade | 32 MB+ | MIT / data public domain | server only | ✅ but as the *validation harness*, not the app runtime |
| Moshier analytic ephemeris (JS port) | Sun–Pluto | ~1″ planets | ~100 KB | public domain | yes | backup option; superseded by astronomy-engine |

### Recommended architecture: `EphemerisProvider` interface, two implementations

```
interface EphemerisProvider {
  longitude(body, jd_tt): { lon, lat, speed }   // geocentric ecliptic of date
  available(body, jd): boolean
}
```

1. **`CoreProvider`** (default, always bundled):
   - Sun, Moon, Mercury…Pluto → `astronomy-engine` (MIT, ±1′).
   - Chiron, Ceres, Pallas, Juno, Vesta, Eris, mean/true lunar Node →
     **Chebyshev packs**: a Python pipeline (`tools/make_packs.py`, using
     `astroquery`/Horizons or Skyfield + small-body SPKs) samples geocentric
     ecliptic longitudes daily across 1900–2100, fits per-body piecewise
     Chebyshev polynomials (32-day segments, degree ~10), and emits compact
     JSON/binary packs. Evaluation in TS is ~20 lines. Typical error ≲1″ —
     far beyond astrological need. The packs ship inside the PWA
     (order 0.5 MB total), so **charts are computed with no internet at all**.
   - The pipeline is rerun to extend coverage (e.g. 1800–2200 for historical
     or long-progression work); pack span is a build parameter.
2. **`SwissProvider`** (optional plug-in): Swiss Ephemeris compiled to WASM plus
   user-supplied `.se1` files (the user downloads them from Astrodienst
   themselves, respecting the redistribution restriction). Used privately, or by
   us in CI as a second opinion. If the project ever goes commercial/public with
   this provider, the CHF 750 professional licence resolves the AGPL question.

**Validation:** golden tests compare `CoreProvider` output at ~200 random
datetimes against Skyfield/Horizons references committed to the repo. Target:
< 0.01° disagreement for asteroids, < 0.02° for planets.

Lunar Node: computed analytically (mean node) with true-node option via
astronomy-engine's lunar theory. Black Moon Lilith (mean lunar apogee) is a
closed-form series — cheap to add, offered as a toggle per the agreed extended
body set.

### 2a. Birth data form (spec 1a)

Fields: **name/label · date of birth · time of birth · time accuracy · place**.

- **Place**: type-ahead against a **bundled offline gazetteer** — the GeoNames
  `cities15000` subset (~25k places, ~2 MB compressed) with name, country,
  lat/lon, IANA timezone. Online mode can optionally query the full GeoNames or
  Nominatim APIs for obscure villages; offline mode also accepts manual
  lat/lon + timezone entry.
- **Timezone & historical DST**: the resolved IANA zone (e.g. `Europe/London`)
  is evaluated **for the birth instant** using the browser's built-in IANA
  database (`Intl` API + the Temporal polyfill) — this handles historical
  oddities (double summer time 1941–45, pre-1971 rules) without shipping our own
  tz database. A manual UTC-offset override field covers disputed cases.
- **Time accuracy** (optional): `exact / ±5 min / ±30 min / ±2 h / unknown`.
  Consequences, shown in the UI rather than silently ignored:
  - error bars on the Ascendant/MC and house cusps (±30 min ≈ ±7° ASC);
  - below a threshold, house placements and Moon sign near a cusp are flagged;
  - `unknown` → solar chart (sunrise or noon, user choice), houses greyed out,
    interpretations that depend on houses/angles suppressed or hedged.

## 3. Chart graphics (spec 2)

Hand-rolled **SVG** (no chart library dependency): full control over glyph
placement, hit areas, and styling; trivially exportable to PNG/PDF; identical
rendering across web/iPad/Android. The mock-up in
[`mockup/chart.html`](../mockup/chart.html) demonstrates the approach with real
aspect-finding code running on illustrative positions.

Wheel anatomy (outside → in): zodiac ring with sign glyphs and 5°/1° ticks →
house ring with cusp lines (angles emphasised) and house numbers → planet ring
with glyphs + degree labels (collision-avoidance nudging for stellia) → central
**aspect hub** where aspect lines are drawn chord-wise between planet positions.
An optional outer **transit/synastry ring** overlays a second chart (§4).

### 3a. Interactive aspects (spec 2a)

Clicking (or tapping — everything is touch-first) is supported on **three
redundant targets**, because thin chords are poor touch targets:

1. the **aspect line** itself, with an invisible 12px-wide hit-stroke under it;
2. either **planet glyph** — highlights all that planet's aspects, panel lists
   them;
3. an **aspect grid** (the classic triangular matrix, shown beside/below the
   wheel) — each cell is a large reliable target and doubles as legend.

Selecting an aspect dims all others, highlights the two planets, and opens the
info panel with **progressive disclosure**: level 1 = the fact (planets, aspect,
orb, applying/separating); level 2 = "More" expands the interpretation in the
currently selected style (§6), plus how this aspect is modified by its
neighbours (§6 combination) and technical detail (exact angle, houses/signs
involved).

### 3b. Orb-tightness shading (spec 2b)

As suggested: **opacity encodes tightness**. `opacity = 0.25 + 0.75 · (1 −
orb/maxOrb)` — an exact aspect is fully saturated, one at the edge of orb is a
whisper, with a 0.25 floor so nothing becomes invisible (accessibility).
Line *width* also steps up for orbs < 2° (partile aspects get a subtle glow), so
the encoding is redundant (not colour/opacity alone). A legend swatch explains
the ramp. This is implemented live in the mock-up.

### 3c. Standard orbs (spec 2c)

Defaults follow mainstream modern practice; every value is editable in settings
(stored per-user, per-chart-type):

| Aspect | angle | base orb | if Sun/Moon involved |
|---|---|---|---|
| Conjunction ☌ | 0° | 8° | 10° |
| Opposition ☍ | 180° | 8° | 10° |
| Trine △ | 120° | 8° | 9° |
| Square □ | 90° | 7° | 8° |
| Sextile ⚹ | 60° | 5° | 6° |
| Quincunx ⚻ | 150° | 2.5° | 3° |
| Semi-sextile, semi-square, sesquiquadrate, quintile (optional, off by default) | 30/45/135/72° | 2° | 2° |

Transit orbs are tighter (majors 3°, moon 5°? — configurable preset “transit
orb set” defaulting to 3°/1° minors), synastry slightly tighter than natal.
Asteroid-to-asteroid aspects default to 3° to limit noise.

### 3d. Glyphs (spec 2d)

Solar Fire's glyph set is the copyrighted property of Esoteric Technologies, so
we do not copy it. Two compliant routes, both attractive and uniform:

1. **Astromoony font** (free, on GitHub; includes planets, Pluto, Ceres,
   Pallas, Juno, Vesta, Chiron and even Eris) — webfont-subset the ~40 glyphs we
   need (~10 KB).
2. **Own SVG glyph set** (recommended end-state): a single hand-tuned SVG
   `<symbol>` per body/sign/aspect, drawn on a common 100×100 grid with uniform
   stroke weight. Guarantees pixel-identical rendering on every platform (system
   fonts differ wildly for U+26B3–U+26B7 and Eris U+2BF0), scales crisply, and
   the style (weight, terminals, proportions) can be tuned to taste — a
   Solar-Fire-*like* aesthetic without copying outlines.

The mock-up uses styled Unicode glyphs (adequate on macOS) and notes where the
SVG set slots in. Sign glyphs get their element colour (fire/earth/air/water);
planet glyphs stay monochrome-on-dark for legibility, with the selected planet
picking up an accent.

## 4. Synastry & transits (spec 3)

One mechanism serves both: a **bi-wheel** with chart A (natal) inside and
chart B outside, where chart B is either another person's natal chart
(synastry) or the sky at an arbitrary moment (transits).

- **Transits**: date/time picker defaulting to *now*, plus a **time slider**
  (day/week/month/year steps) that animates the outer ring — transiting aspect
  lines to natal points fade in/out through orb, which makes station-and-retrograde
  passes over a natal point viscerally visible. A "next 12 months" list view
  enumerates exact hits (computed by root-finding on the longitude difference —
  cheap with our providers).
- **Synastry**: pick any two saved charts; inter-chart aspects use the synastry
  orb set; the aspect grid becomes the rectangular synastry grid (A's planets ×
  B's planets). House overlays ("her Sun falls in his 7th") are listed and
  clickable like aspects. Interpretations draw on the relationship theme
  engine (§7d).
- **Progressions** (needed for §6c energy-pattern style): secondary progressions
  (day-per-year) are a trivial reuse — progress the datetime, compute with the
  same providers, display in the same bi-wheel. Long progressions ship in v1 as
  agreed; short/minor progressions are a later toggle.
- Composite/Davison charts: straightforward extensions (midpoint composite needs
  only arithmetic; Davison reuses the ephemeris) — flagged as v2, not in scope.

## 5. Saved charts & local database (spec 4)

**IndexedDB** via Dexie.js. Schema:

```
people(id, name, notes, tags)
charts(id, personId, kind: natal|event|horary, date, time, tzOffsetUsed,
       timeAccuracy, place{name,lat,lon,tz}, computed{positions,cusps,aspects},
       schemaVersion, createdAt, updatedAt)
settings(orbSets, bodyToggles, style, theme)
interpretations_cache(chartId, styleId, sectionId, text, source: library|llm)
```

- Computed positions are cached but recomputable — the birth data is the source
  of truth, so ephemeris upgrades can re-derive everything.
- **Export/import**: one-tap JSON export (single chart or whole database) to
  file/share-sheet — this is also the answer to browser storage eviction and
  device migration. `navigator.storage.persist()` is requested to make eviction
  unlikely.
- No cloud, no accounts, by design. (A future optional sync could encrypt-and-push
  the JSON export to any dumb file host; deliberately out of scope.)

## 6. Placidus houses (spec 5)

Placidus is the default (per spec, applied to every natal chart) with the
standard algorithm: obliquity + local sidereal time → MC/ASC exactly, then
intermediate cusps 11,12,2,3 by the iterative semi-arc method (trisection of
diurnal/nocturnal arcs, converges in ~5 iterations; well-documented and
implemented from the literature — also available for cross-checking in
`circular-natal-horoscope-js`, an existing open-source TS implementation).

Known edge case handled explicitly: Placidus is **undefined above the polar
circles** (|lat| > ~66.5°). Behaviour: automatic fallback to Porphyry with a
visible notice on the chart, matching common software practice. House system is
switchable in settings (Whole Sign, Koch, Equal, Porphyry) but Placidus remains
the default and the basis of interpretations.

Golden tests validate cusps against Swiss Ephemeris output for a spread of
latitudes and dates.

## 7. Interpretations engine (spec 6) — hybrid, with aspect combination

### Architecture

Two layers, per our agreed hybrid approach:

1. **Deterministic library layer (offline, always available).** A curated,
   versioned text library — the app's knowledge base — plus a **composition
   engine** that assembles chart-specific readings from it.
2. **LLM enrichment layer (online, optional).** When a network and API key are
   present, the composed reading (fragments + structure + tension report, see
   below) is handed to an LLM **as constrained source material** with
   instructions to improve flow and voice *without adding astrological claims
   not present in the input*. Output is cached locally per chart+style. Offline,
   the deterministic composition is shown as-is — complete sentences joined by
   template connectives, slightly stiffer but fully functional.

### The text library

Fragments are keyed by `(factor, style)` where a factor is e.g.
`Moon-square-Saturn`, `Sun-in-Pisces`, `Saturn-in-house-10`,
`Chiron-conj-Jupiter`. Each fragment carries metadata used by the composer:

```yaml
key: moon-square-saturn
styles: {jungian: "...", mundane: "...", energy: "...", minimal: "..."}
themes:  {emotional-security: -0.8, discipline: +0.7, inhibition: +0.6}
valence: challenge          # challenge | flowing | neutral
weight_hints: [moon, saturn]
```

The `themes` vector is a small hand-assigned signature over a controlled
vocabulary of ~40 psychological themes (security, autonomy, expression,
boundary, expansion, wounding, …), signed for direction. This is what makes
combination computable.

### Combining aspects — how each is modified by all the others

This was the specific request, so in detail. The composer works per **planet
cluster**, then per **chart**:

1. **Weighting.** Every aspect gets a salience score:
   `w = tightness(orb) × planetWeight(A) × planetWeight(B) × aspectWeight`,
   where luminaries and angle rulers weigh more, and partile aspects dominate.
   This ordering decides what leads a reading and what is a footnote — the same
   scale that drives the visual opacity (§3b), so what you *see* strongest is
   what you *read* first.
2. **Shared-planet clustering.** Aspects sharing a planet are composed together.
   If the Moon is square Saturn *and* trine Jupiter, the two fragments are
   rendered as one passage: the higher-weight aspect leads, the other is
   attached with a **relation connective** chosen by comparing theme vectors:
   - vectors broadly aligned → *reinforcing* connective ("…and this is deepened
     by…");
   - vectors opposed on a shared theme → *counterpoint* connective ("…though
     Moon trine Jupiter offers an easier emotional outlet, softening the
     Saturnian restraint…");
   - orthogonal → plain conjunction ("separately, …").
3. **Chart-level tension report.** Across clusters, the composer scans all
   aspect pairs (n aspects → n(n−1)/2 pairs, trivially cheap at chart scale) for
   **theme-vector dot products** below a negative threshold — genuinely
   contradictory indications (e.g. `expansion +` vs `expansion −` on the same
   theme). These are **not averaged away**. Modern psychological astrology
   treats contradiction as real: people contain opposing patterns expressed in
   different contexts or life phases. So contradictions are *surfaced
   explicitly* in a dedicated "Tensions & polarities" section: "Your chart holds
   both X (from A) and Y (from B); expect to oscillate, or to live one at work
   and the other at home." The style layer renders this differently — Jungian
   frames it as material for integration of opposites; Minimalist just states
   both facts and the tension.
4. **Honest limits, stated in-app.** With ~15 bodies and 6 aspect types the
   pairwise combination space is ~10⁴ and the higher-order space is unbounded —
   no library can hand-author it. The theme-vector mechanism is deliberately
   *shallow but predictable*: it composes pairwise relations and flags
   contradictions; it does not pretend to synthesise a whole psyche. Where the
   composer detects a dense knot (≥3 mutually-aspecting planets, i.e. t-squares,
   grand trines, yods — detected geometrically as aspect *patterns* and given
   their own library entries), it prefers the pattern-level text over pairwise
   assembly. The LLM layer, when available, is the only component allowed to
   attempt higher-order synthesis — and it is constrained to the fragments and
   tension report as source material precisely so its fluency cannot smuggle in
   fabricated astrology.

### 7a–d. The four styles (spec 6a–6d)

Each fragment is authored in four voices; the UI has a global style switcher and
per-section override. Divergences from the mainstream are flagged where taken:

- **Jungian (6a)** — archetypal and depth-psychological: planets as archetypes,
  hard aspects as tension-bearing complexes and invitations to integration,
  shadow and projection language for oppositions and the 7th/8th houses, Chiron
  and the nodal axis as individuation motifs. Anchored in the Greene/Sasportas
  lineage of psychological astrology (in approach, not in copied text — all
  fragments are authored fresh for this project).
- **Mundane (6b)** — outer-world and situational: the same factor described as
  circumstances, timing, and concrete life areas ("periods when responsibilities
  cluster", "career structures that reward patience"), house emphasis over
  psyche. For transits especially, this is the natural register.
- **Energy patterns (6c)** — cyclical/dynamic register: factors as energies with
  build/peak/release phases. Illustrated **with respect to the natal chart and
  long progressions** as specified: progressed-to-natal cycles (progressed Moon
  cycle ~27.3 yr, progressed Sun sign changes ~30 yr, the Saturn cycle) are
  drawn as a **timeline/spiral view** alongside the wheel, each cycle annotated
  with growth-phase language (initiation → consolidation → harvest → release).
  Short progressions are the agreed later addition and slot into the same view.
- **Minimalist & matter-of-fact (6d)** — one to three plain sentences per
  factor, no metaphor, no hedging, explicitly non-mystical. Doubles as the
  accessibility/skim mode and is the cheapest to author, so it is written first
  for full coverage while richer styles grow over time (coverage indicator shown
  per style).

Authoring plan: minimalist style for all factor keys first (machine-checkable
coverage), then the ~200 highest-salience keys (10 planets × signs, planets in
houses, major pairwise aspects of Sun–Saturn + Chiron) in all four styles;
long-tail asteroid texts follow usage.

## 8. Themes (spec 7)

Themes are *computed dossiers*: each gathers a defined set of chart factors,
runs them through the §7 composer, and renders in the selected style. Each theme
states its factor list on screen — no hidden inputs.

- **7a. The Chiron wound** — Chiron's sign (generational tone), house (arena of
  the wound), aspects (channels; hard aspects to luminaries/angles weighted
  highest), plus 12th-house and Pisces emphasis as secondary signature. Rendered
  as wound → coping pattern → gift arc (the mainstream contemporary reading);
  transits of/to Chiron feed the same dossier for "as it may appear in life".
- **7b. Saturnal teachings** — Saturn sign/house/aspects, Saturn as dispositor,
  current and upcoming Saturn transits and the return schedule (ages ~29/58/87
  computed exactly from the ephemeris, listed with dates). Framed as
  curriculum: what is demanded, what matures, where authority is contested.
- **7c. Sun–Moon relationship** — the aspect (or lack) between them, elemental
  compatibility of their signs, the **natal lunation phase** (8-fold, from
  Sun–Moon elongation — a Rudhyar-derived reading, flagged as such), dispositor
  relations, and house axis. Rendered as the conscious-purpose vs
  emotional-need dialogue and its reflection in personality.
- **7d. Intimate relationships & compatibility** — natal capacity first (Venus,
  Mars, Moon, 7th/8th cusps and tenants, Juno by house/sign/aspect — Juno
  earning its place in the spec's body list here), then **prospective** reading
  (patterns sought and repeated) or **specific synastry** when a second chart is
  selected: inter-aspect grid filtered to relationship-significant pairs,
  house overlays, and the §7 contradiction machinery applied *across* charts
  ("his Saturn on her Moon steadies and inhibits" — both stated).
- **7e. Career dynamics** — MC sign + ruler + its condition, 10th/6th/2nd house
  tenants, Saturn (again, flagged as shared factor with 7b rather than
  double-counted), North Node house/sign as direction-of-growth (modern usage,
  flagged), current Jupiter/Saturn transits to the MC axis for timing.

## 9. Application architecture

```
src/
├── ephemeris/     providers (core, swiss-plugin), chebyshev eval, node/lilith
├── chart/         julian day, sidereal time, houses (placidus + fallbacks),
│                  aspects, patterns (t-square, grand trine, yod), progressions
├── render/        svg wheel, bi-wheel, aspect grid, glyph symbol set, timeline
├── interpret/     library loader, theme vectors, composer, tension report,
│                  styles, llm-enrichment (optional, keyed)
├── store/         dexie schema, export/import, settings
├── ui/            form, panels, style switcher, saved-chart browser
└── pwa/           service worker, install, persistence request
tools/             make_packs.py, golden_refs.py  (Python; runs on the MacBook)
data/              chebyshev packs, gazetteer, text library (yaml → compiled json)
mockup/            static demonstrator (this proposal's mock-up)
```

Stack: **TypeScript + Vite + Svelte** (small bundle, reactive UI, no runtime
framework tax; the render layer is framework-agnostic SVG so Svelte is
replaceable), Dexie for storage, Vitest for tests, no other runtime
dependencies beyond `astronomy-engine`. Total app budget ≈ 3–4 MB including
ephemeris packs and gazetteer — comfortably offline-cacheable.

### Milestones

1. **M1 — compute core** (ephemeris providers + packs pipeline + houses +
   aspects, golden-tested): the risk burns down here; everything after is UI
   and writing.
2. **M2 — natal wheel** (render layer + form + IndexedDB save/load) = usable
   personal tool.
3. **M3 — interpretations** (library schema, composer, minimalist style
   coverage, style switcher, themes 7a–7c).
4. **M4 — synastry/transits/progressions** (bi-wheel, slider, hit list, themes
   7d–7e, energy timeline).
5. **M5 — PWA polish** (service worker, install flow, export/import, glyph SVG
   set, LLM enrichment option) + deploy to the shared host.

### Risks & mitigations

- *Placidus at high latitude* → Porphyry fallback, tested (§6).
- *Historical timezones* → IANA via `Intl`/Temporal + manual override (§2a).
- *Browser storage eviction* → persist() + export/import (§5).
- *Text-library authoring effort is the real long pole* → minimalist-first
  coverage strategy + composer designed to degrade gracefully to key facts when
  a fragment is missing (§7).
- *Licensing* → default build is MIT/public-domain-data only; Swiss Ephemeris
  strictly an opt-in private plug-in unless the CHF 750 licence is bought (§2).

- Python binding (AGPL): [astrorigin/pyswisseph](https://github.com/astrorigin/pyswisseph); asteroid file layout: [asteroid ephemeris files doc](https://github.com/astrorigin/pyswisseph/blob/master/docs/ephemerides/asteroids/asteroid_ephemeris_files.rst)
- MIT ephemeris engine: [cosinekitty/astronomy (Astronomy Engine)](https://github.com/cosinekitty/astronomy), [npm package](https://www.npmjs.com/package/astronomy-engine)
- Existing open-source TS chart calculations incl. Placidus: [0xStarcat/CircularNatalHoroscopeJS](https://github.com/0xStarcat/CircularNatalHoroscopeJS); SVG wheel reference: [Kibo/AstroChart](https://github.com/Kibo/AstroChart)
- Free astronomical glyph font incl. asteroids: [RobertWinslow/Astromoony-Font](https://github.com/RobertWinslow/Astromoony-Font)
